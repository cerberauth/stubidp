## CLI flags

| Flag                                  | Required | Description                                                                                                                               |
| ------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `--client-id`                         | No       | OAuth 2.0 client ID your application will use. Auto-generated (e.g. `brave-falcon-3a9f12`) when omitted.                                  |
| `--client-secret`                     | No       | OAuth 2.0 client secret your application will use. Auto-generated (43-char random secret) when omitted.                                   |
| `--public-client`                     | No       | Configure as public client (no `client_secret`, `token_endpoint_auth_method=none`). For SPAs and native apps.                             |
| `--redirect-uri`                      | No\*     | Redirect URI registered for your client. Required unless `STUBIDP_REDIRECT_URI` is set.                                                   |
| `--jwks-file`                         | No       | Path to a JWKS JSON file. A key pair is auto-generated when omitted. See [Signing keys](#signing-keys).                                   |
| `--skip-prompt`                       | No       | Skip login and consent UI and auto-approve every interaction. Intended for E2E tests and automation.                                      |
| `--default-user`                      | No       | JSON object of OIDC claims returned for every authenticated user (e.g. `'{"sub":"alice","email":"alice@example.com"}'`).                  |
| `--rate-limit-window-ms`              | No       | Rate limit time window in milliseconds. Default: `900000` (15 min).                                                                       |
| `--rate-limit-max`                    | No       | Max requests per IP per window. Default: `100`.                                                                                           |
| `--rate-limit-disabled`               | No       | Disable rate limiting entirely.                                                                                                           |
| `--enable-registration`               | No       | Enable dynamic client registration (RFC 7591) and management (RFC 7592) via `/reg`.                                                       |
| `--registration-initial-access-token` | No       | Bearer token required to call `POST /reg`. Omit for open registration.                                                                    |
| `--trust-proxy`                       | No       | Trust reverse proxy headers (`X-Forwarded-*`). Enable when running behind a reverse proxy or load balancer.                               |
| `--https-redirect`                    | No       | Redirect HTTP requests to HTTPS and enable CSP `upgrade-insecure-requests`. Enable in production behind TLS termination.                  |
| `--security-headers`                  | No       | Enable security headers (CSP, HSTS, etc.) via helmet. Enable when deployed; omit for local development.                                   |
| `--scopes`                            | No       | Comma-separated list of supported OIDC scopes. Default: `openid,offline_access,email,profile,phone,address`.                              |
| `--claims`                            | No       | JSON object mapping scope names to claim arrays. Overrides auto-derived claims (e.g. `'{"openid":["sub"],"email":["email"]}'`).           |
| `--access-token-format`               | No       | Access token format: `opaque` (default) or `jwt`. JWT access tokens carry identity claims (`sub`, `email`, etc.).                         |
| `--access-token-ttl`                  | No       | Access token lifetime in seconds (also applies to client credentials tokens). Default: `3600`.                                            |
| `--id-token-ttl`                      | No       | ID token lifetime in seconds. Default: `3600`.                                                                                            |
| `--refresh-token-ttl`                 | No       | Refresh token lifetime in seconds (14 days). Default: `1209600`.                                                                          |
| `--session-ttl`                       | No       | Login session lifetime in seconds (14 days). Default: `1209600`.                                                                          |
| `--id-token-includes-userinfo-claims` | No       | Include email/profile/etc. claims directly in the ID token instead of requiring a separate `/me` call. Default: `false` (spec-compliant). |
| `--interaction-path`                  | No       | Base path for the login/consent UI. Default: `/interaction`.                                                                              |
| `--disable-telemetry`                 | No       | Don't load the Plausible telemetry script on the HTML pages. Also disabled by `DO_NOT_TRACK=1`. See [Telemetry](#telemetry).              |

When `--client-id` or `--client-secret` are omitted, the generated values are printed in the startup table so you can copy them into your application config.

Every CLI flag can also be set via an environment variable (see below). Environment variables take effect when the flag is not passed explicitly.

## Telemetry

The HTML pages StubIdP serves (home, login, consent, sign-out) load a small [Plausible](https://plausible.io) script that reports to `a.cerberauth.com`, a CerberAuth-operated Plausible instance. It is cookie-free and collects no personal data. The OIDC endpoints themselves (`/auth`, `/token`, …) are never instrumented.

What is recorded:

- **Page views** of the pages above. Query strings and fragments are dropped, and the per-flow interaction id in `/interaction/:uid` is replaced with `:id`.
- **Clicks and form submits**: `Create Client`, `Discovery Click`, `Login Submit`, `Login Cancel`, `Consent Allow`, `Consent Deny`, `Logout Confirm`, `Logout Cancel`, plus outbound link clicks.

Usernames, client IDs, scopes and tokens are never sent. Nothing is sent when the page is served from `localhost`, and `--skip-prompt` skips the login and consent pages entirely.

To turn it off, use any of:

```bash
stubidp --disable-telemetry ...
STUBIDP_DISABLE_TELEMETRY=true stubidp ...
DO_NOT_TRACK=1 stubidp ...
```

When disabled, the script tag is not rendered at all and the `Content-Security-Policy` no longer allows connections to the telemetry host. On Cloudflare Workers, set `STUBIDP_DISABLE_TELEMETRY` to `true` in `vars`.

This is separate from the server's own OpenTelemetry export (`OTEL_EXPORTER_OTLP_ENDPOINT` and friends), which is off unless you configure an endpoint and sends to your collector, not to CerberAuth.

Individual visitors can also opt out by running `localStorage.plausible_ignore = 'true'` in their browser console.

## Database

StubIdP supports two database backends for persisting OIDC session state.

### In-memory (default)

When no database is configured, an in-memory store is used. Sessions are lost on restart — suitable for most local development workflows.

### SQLite

```bash
STUBIDP_DATABASE_DIALECT=sqlite STUBIDP_DATABASE_URL=./stubidp.db stubidp \
  --redirect-uri http://localhost:8080/callback
```

### PostgreSQL

```bash
STUBIDP_DATABASE_DIALECT=postgresql \
STUBIDP_DATABASE_URL=postgresql://user:pass@localhost:5432/stubidp \
stubidp \
  --redirect-uri http://localhost:8080/callback
```

<Aside type="tip">
  For ephemeral CI environments, the in-memory default (no database config) is usually the right choice.
</Aside>

## Issuer URL

The `STUBIDP_ISSUER` value is embedded in issued tokens as the `iss` claim and must match what your application validates.

- **Local dev** — defaults to `http://localhost:8484`, no change needed.
- **Cloudflare Workers** — derived automatically from the incoming request URL, no override required.
- **Custom domain** — set `STUBIDP_ISSUER=https://idp.example.com` to match your deployed URL.

## Automation and E2E testing

StubIdP has two mechanisms for running auth flows without any human interaction.

### `--skip-prompt` / `STUBIDP_SKIP_PROMPT`

When this flag is set, every redirect to the login or consent screen is silently auto-approved. The browser (or test runner) follows the normal OIDC redirect chain and receives the authorization code at the redirect URI without any UI being rendered.

```bash
STUBIDP_SKIP_PROMPT=true stubidp --redirect-uri http://localhost:3000/callback
```

### `GET /interaction/:uid/auto`

A headless endpoint that is always available regardless of `--skip-prompt`. Navigate the browser to this URL instead of `/interaction/:uid` to complete the current interaction step programmatically. Useful when you want UI available by default but need headless completion in specific test cases.

If `--interaction-path` / `STUBIDP_INTERACTION_PATH` is set, this endpoint moves with it (e.g. `/auth/:uid/auto`).

### `--default-user` / `STUBIDP_DEFAULT_USER`

Provide a JSON object of standard OIDC claims that StubIdP will include in the ID token and UserInfo response for every authenticated session. The `sub` field controls the subject identifier used during `--skip-prompt` auto-login; all other fields are returned as-is.

```bash
STUBIDP_DEFAULT_USER='{"sub":"alice","name":"Alice Example","email":"alice@example.com","email_verified":true}' \
STUBIDP_SKIP_PROMPT=true \
stubidp --redirect-uri http://localhost:3000/callback
```

Supported fields: any standard [OIDC claims](https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims) (`name`, `given_name`, `family_name`, `email`, `email_verified`, `picture`, `locale`, `phone_number`, etc.) plus arbitrary custom claims.

<Aside type="tip">
  `--default-user` is also useful without `--skip-prompt`. Any user who logs in through the UI will receive these claims
  in their tokens, regardless of the username they enter.
</Aside>

### `login_hint` as subject

When `--skip-prompt` is active and no `--default-user` is set, StubIdP requires a `login_hint` parameter in the authorization request. The value must be a valid email address or E.164 phone number. It is used as the subject identifier (`sub`) and automatically populates the `email` or `phone_number` claim to match.

```bash
# Authorization request includes: login_hint=alice@example.com
STUBIDP_SKIP_PROMPT=true stubidp --redirect-uri http://localhost:3000/callback
# Result: sub = "alice@example.com", email = "alice@example.com"
```

<Aside type="caution">
  If `login_hint` is missing or not a valid email or E.164 phone number, the flow errors. Set `--default-user` if you
  need a fixed identity without per-request hints.
</Aside>

## Access token format

By default, access tokens issued by StubIdP are opaque strings — identity claims (`email`, `profile`, etc.) are only
available via the [UserInfo endpoint](/reference/endpoints#userinfo). Some providers instead issue access tokens as
JWTs carrying identity claims directly, which resource servers can validate locally without an extra UserInfo call.
Set `--access-token-format jwt` (or `STUBIDP_ACCESS_TOKEN_FORMAT=jwt`) to match that behavior.

```bash
STUBIDP_ACCESS_TOKEN_FORMAT=jwt stubidp --redirect-uri http://localhost:3000/callback
```

The resulting access token is a signed JWT containing `sub` plus any claims from `--default-user` (or auto-populated
from `login_hint`), alongside standard OAuth claims (`scope`, `client_id`, `iss`, `aud`, `exp`, `iat`, `jti`).

<Aside type="tip">
  Access token claims always include the full identity claim set regardless of requested scope, since it mirrors what a
  real resource server would expect. ID token claims are controlled separately — see below.
</Aside>

## Signing keys

By default StubIdP generates a new RS256 key pair on every start, so ID tokens issued before a restart no longer validate (for example, `/session/end` fails with `could not validate id_token_hint`). To keep the key stable, generate a JWKS document once:

```bash
stubidp-jwks --out jwks.json          # or: npm run jwks:generate -- --out jwks.json
```

`stubidp-jwks` accepts `--kid <id>` to set the key ID and prints to stdout when `--out` is omitted. The file contains a private key, so do not commit it.

Then provide it either as a file or inline, whichever suits your environment:

```bash
stubidp --jwks-file jwks.json --redirect-uri http://localhost:3000/callback
# or
STUBIDP_JWKS="$(cat jwks.json)" stubidp --redirect-uri http://localhost:3000/callback
```

`--jwks-file` takes precedence over `STUBIDP_JWKS`. On Cloudflare Workers, store the JSON as the `STUBIDP_JWKS` secret; see [Cloudflare Workers](./deployment/cloudflare-workers/#persistent-signing-key).

## Token and session lifetimes

StubIdP is a dev stub, so the defaults are long-lived (1 hour for access and ID tokens, 14 days for refresh tokens and
sessions). Override them in seconds with `--access-token-ttl`, `--id-token-ttl`, `--refresh-token-ttl` and
`--session-ttl` (or the matching `STUBIDP_*_TTL` variables) to exercise expiry and refresh handling in your app.

```bash
STUBIDP_ACCESS_TOKEN_TTL=30 stubidp --redirect-uri http://localhost:3000/callback
```

Values must be positive integers; StubIdP fails to start otherwise.

## ID token claims

By default (spec-compliant), the ID token only carries `sub` — claims requested via non-`openid` scopes (`email`,
`profile`, etc.) are only returned via the [UserInfo endpoint](/reference/endpoints#userinfo). Real IdPs behave this
way too: an RP using `response_type=code` is expected to call UserInfo for profile data. Set
`--id-token-includes-userinfo-claims` (or `STUBIDP_ID_TOKEN_INCLUDES_USERINFO_CLAIMS=true`) if your client reads
claims straight off the ID token and you don't want to implement a UserInfo call.

```bash
STUBIDP_ID_TOKEN_INCLUDES_USERINFO_CLAIMS=true \
STUBIDP_DEFAULT_USER='{"sub":"alice","email":"alice@example.com","email_verified":true}' \
stubidp --redirect-uri http://localhost:3000/callback
```
